# Server plan: Life on an always-on host (22 Oct 2026)

Explanation and plan: how Life moves from "runs on the owner's Mac" to "runs on a server, with the Mac as one
optional edge", what each source becomes, what it costs, and the decisions the owner has to make first. Research only:
nothing here is built yet. It follows the [platforms and modules plan](2026-10-22-platforms.md), whose phase 1
(Better-T-Stack) left the slots this plan fills.

## Why

Life runs where the Mac is. When the Mac sleeps or is offline, the connector, the nightly and the archive stop, and
deleted messages arriving meanwhile are lost for good (the archive copies stores every 5 s, only while it runs). A
server is always on. The open-source case points the same way: a self-hoster may prefer a box they control to an app
with Full Disk Access on their laptop. A Mac-only install stays a choice; the server becomes the other one, from the
same codebase (the roadmap's two release channels).

## The shape: a hub and edges

The server is the hub: the memory (`truth/`, `memory/`), the archive, the model calls, the connector, the nightly.
Everything that can be read over the network is read there. The edges are optional and push to the hub when they are
online; the hub never waits on one:

- **The Mac companion** (Life.app, which already holds Full Disk Access): ships what only a Mac can read (Apple Notes,
  iMessage if not bridged, Apple Mail if not on IMAP, an allowlist of folders) and offers a read-only file API.
- **lifelog**: unchanged, already a REST input.
- **The owner's Chrome**: driven by his agent, not by Life (below).

The seam exists: the platforms plan already reads WhatsApp and Notes "from an archive copied on a Mac" on a host that
cannot read them. The companion makes that copy continuous instead of a one-time import.

## Sources, today and on a server

| Source | Today (Mac) | On the server | Risk |
|---|---|---|---|
| lifelog | REST | Same | None |
| Mail | Apple Mail's store | IMAP or the Gmail API (`gog`, already used for Google Tasks) | Low |
| Contacts | AddressBook databases | CardDAV (iCloud takes an app-specific password) or Google People | Low |
| Git | Repos under `repos` | Clones from the forge, or the companion | Low |
| Telegram | Beeper Desktop's index | TDLib or gramjs (official user API, full history) | Low |
| Signal | Not read | mautrix-signal or signal-cli (a linked device is allowed) | Low |
| WhatsApp | The Mac app's store | whatsmeow (Go, what mautrix-whatsapp is built on), as a linked desktop device: about a year of history at link | Against WhatsApp's terms; bans rare for one personal account |
| Instagram | Beeper | mautrix-instagram (the only one tracking Meta's 2026 DM protocol change) | High: breakage and account checkpoints |
| LINE | Beeper | beeper/line (MIT; it takes the place of LINE's Chrome extension session) | Medium, fragile |
| iMessage | `chat.db` | Corten (`lrhodin/corten-matrix`, on OpenBubbles' rustpush): a hardware key extracted once from a Mac, no Mac at run time; history through iCloud Keychain trust. Else the companion ships `chat.db` | High: a hobby project, Apple can block the key, Keychain trust widens the blast radius |
| Apple Notes | NoteStore + note archive | The companion only (no server API worth trusting) | None while the Mac is the edge |
| Actions | Apple Reminders (remctl) or Google Tasks | Google Tasks; Reminders through the companion | Low |
| Files | Not read | Google Drive or Dropbox by API (stable tokens); iCloud Drive pushed by the companion. rclone's iCloud backend is experimental and needs a 2FA code every 30 days: opt-in only | Low / medium |

Every row is a source descriptor in `SOURCES`; nothing branches on a name. A network source on the server reports
its link state through `missing()` like a Mac store does today.

### The archive gets better, not worse

No network replays a deleted message: WhatsApp, Telegram, Instagram and iMessage all send "delete id X", and Matrix
bridges turn that into a redaction that wipes the content. So the server saves every message the moment it arrives,
in Life's own archive, and records the delete as a new row beside it. Because the server is always on, that catches
what the Mac's 5-second copy misses whenever the Mac is closed. It needs new archive tables: the owner's OK first
(an invariant). The existing archive files are copied to the server once, never moved or rewritten; the Mac keeps its
copy until the owner says otherwise.

### Matrix or the libraries directly

Two ways to run the messaging connectors:

- **Matrix**: a small homeserver (continuwuity, one Rust binary) plus the mautrix bridges, with Life as an
  appservice. Every network looks the same to Life, and the bridges are maintained by people who track each protocol.
  Beeper's `bbctl` is not an option for a self-hosted Life: its bridges talk to Beeper's servers.
- **Libraries**: whatsmeow, TDLib, signal-cli inside Life's container. Less to run, but Life tracks each protocol.

Recommendation: Matrix. Instagram and LINE are only maintained as bridges, and one interface for read and send keeps
"one way to do each thing". Cost: one more container and monthly bridge upgrades.

### Sends

Today a send happens outside Life (his agent through Beeper), and SECURITY.md lists that as policy, not enforcement.
With bridges, Life can send itself, so the rule moves into code: a send needs the owner's yes on the exact text, held
in the ledger like an action, and the connector's `reply` tool is the one way in. That is a new send path: it
changes an invariant ("never add a send") and needs the owner's decision.

## Models

The invariant stays: his subscriptions first. Claude Code and Codex run headless on Linux with a long-lived login,
under their own homes as today; an API key or OpenRouter (already in `PROVIDERS`) is the fallback for installs
without a subscription. To verify before building: how long each CLI's headless login lasts on a server.

## Transcription (lifelog's, noted here for the cost)

Transcription is lifelog's, and its own report owns the choice. The numbers that matter for the server: at about
300 hours a month, ElevenLabs Scribe v2 lists at $0.22/h, about €57, so a €100 bill means a plan tier larger than
the use. Self-hosted, NVIDIA Parakeet TDT 0.6B v3 (25 European languages, French included, no Thai) loads in about
2 GB of RAM and runs well above real time on CPU, so 10 hours a day fits on the same 16-vCPU box as Life. Diarization
is the CPU cost: pyannote takes about an hour per audio hour on CPU; sherpa-onnx or `diarize` take a few minutes.
Thai goes to Soniox ($0.10/h, Thai, French and diarization). On a Mac, Parakeet runs 80× or more on the Neural Engine.
Before switching, both are measured against Scribe on about ten of his own noisy recordings.

## The owner's Chrome

Life never browses. His agent does, and datacenter IPs get blocked. The fit is Playwriter: its relay runs on the Mac,
takes a token, shares only the tabs he picks, and is reached from the cloud over Tailscale, in a dedicated Chrome
profile. Since Chrome 136, plain remote debugging no longer works on the default profile, so the CDP-flag route is
closed. When the Mac is off, browser tasks wait; a hosted browser with residential proxies is an opt-in fallback.
This is the agent's tool, not a connector tool.

## Security

What the server holds: the memory, the archive, the model logins and every messaging session key, which can send as
the owner. A compromised server reads everything and sends on every network until each device is unlinked. That is
more than today, where sends need the Mac. The design answers it so:

- No public port but the connector, behind its OAuth issuer, through a Cloudflare tunnel or Caddy; administration and
  the companion over Tailscale only.
- Disks encrypted; secrets from systemd-creds or age, never in the image or in `.env` on disk in clear.
- Matrix end-to-bridge encryption, so the homeserver's database is ciphertext.
- The data repo still has no remote; backups stay restic, encrypted, to a place the owner picks.
- A written runbook to unlink every device (WhatsApp, Signal, Telegram sessions, the Apple ID device) in minutes.
- A VPS provider can read a running machine. Encryption at rest does not change that. Self-hosters who mind can run
  the same image on a box at home (a Mac mini, a NAS).

SECURITY.md's "What leaves the Mac" becomes "What leaves the host", rewritten with the owner, item by item.

## Docker

Docker is the server channel's package: one Compose file, nothing Mac-specific in it.

- `life`: the server, the memory steps, the nightly (Bun, `apps/server`).
- `homeserver` and one container per enabled bridge.
- `tunnel`: cloudflared or Caddy.
- Volumes: the data repo, the archive, bridge state; each encrypted, none baked into the image.

The Mac channel stays Life.app. The services Life.app supervises today become Compose services with restart policies,
and the status plate becomes a page of the web UI (`apps/web`, the roadmap's next item).

## Host

For one owner: a Hetzner CX53 (16 shared vCPU, €29.49 a month) or CAX41 (16 ARM vCPU, €40.99), in the EU, holds Life,
the bridges and Parakeet. DigitalOcean is several times dearer for the same cores. LINE's bridge image is amd64
only, which favours the CX53.

## Phases

1. **Server mode with the network sources.** A headless entry point, the Compose file, the connector served from the
   host, lifelog, Gmail, Google Tasks, the Past calendar, git from the forge. The data repo moves to the server once
   (one Life per data repo: the Mac's services stop when the server's start).
2. **The Mac companion.** Life.app ships Notes, iMessage, Mail and its archive copies to the hub over Tailscale when
   online, and serves a read-only file API on an allowlist set on the Mac.
3. **Messaging connectors.** The homeserver and bridges, Telegram and WhatsApp first; save-on-arrival archive; sends
   behind the owner's yes, if he decides so.
4. **iMessage through Corten**, opt-in, with the companion's `chat.db` as the fallback.
5. **Files**: Google Drive and Dropbox; iCloud Drive through the companion.
6. **Chrome**: Playwriter over Tailscale, documented for his agent.

## Decisions for the owner

1. A VPS (which provider, which country) or a box at home.
2. New archive tables for save-on-arrival.
3. Life sending through bridges, with the yes enforced in code, or sends staying with the agent.
4. The terms risk on WhatsApp and Instagram, and Corten's Keychain trust for iMessage history.
5. Matrix with bridges, or libraries in Life's container.
6. Rewriting SECURITY.md's list of what leaves.
