# No more Beeper: messaging connectors, sends included

Goal: uninstall Beeper Desktop, one network at a time, with every messaging network behind the one source contract:
read, a message event that starts the agent, and a send that Life makes only on his yes to the exact text.

Shape:
- **The source descriptor is the connector.** `Descriptor` (`sources/contract.ts`) gains one optional capability,
  `send(chat, text)`. Nothing branches on a network's name.
- **One local Matrix homeserver** (Synapse on SQLite, in Docker on the Mac) runs the bridges. Its `event_json` is plain
  SQLite, so the archive copies it with one read-only query, as it copies Beeper's `index.db` today. Redacted content is
  kept long enough for the 5 s copy (`redaction_retention_period`).
- **One `bridged` source for every bridge.** Which bridges run is a setting, shown as the source's parts (as Beeper's
  networks are today). A new network is a container and a settings line, no code.
- **The message event**: when a copy saves a message that isn't his (or iMessage's newest changes), Life starts the
  agent with `{kind:"message", source, chat}` (`startAgent`, `events.ts`). life-loops decides what it starts.
- **Sends, enforced in code**: a reply is a decision (`records/decision.ts`) whose option carries the exact text
  (`draft`) and whose `ref` names the chat. `bun life send <decision>` sends it only when he answered that option, with
  no note, and no message came in that chat after it was asked (life-loops' rules of 28 Oct, moved into code). It
  calls the source's `send` and appends one `sent` line to the ledger. A CLI, not a connector tool: the ChatGPT tool
  list stays frozen.

Shape: the descriptor stays the one definition of a network; `send` is one more optional capability on it. Whether a
reply may go is decided once, from `decisionsNow` and the archive, in the send CLI: life-loops' copy of those rules
goes. Starting the agent stays in `startAgent`, one more event kind. Every bridged network shares one copy query and
one `matrix.ts` sender.

State: no new state file. A send is one ledger line (`sent`), per decision. The archive gets new rows in its existing
tables. The bridges' state (Synapse's database, the device links) lives in their Docker volumes. iMessage's last seen
message is in memory.

Deletes: Beeper's `index.db` reading and fixture, Beeper Desktop in `keptStores`, Beeper `send_message` and `imsg` in
life-loops' brief, life-loops' send rules (now in code), the old source name after the migration, Beeper in docs.
