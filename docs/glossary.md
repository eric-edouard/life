# Glossary

Reference: every name Life uses for one of its concepts, with what it means. One name per concept, the same in the
docs, the app, the email, the connector and the code. A name that is not here is a plain English word.

**Word** is the name in code and stored data today. **Planned** is a decided rename that hasn't landed yet: until it
does, code and stored data use the Word, and the PR that lands it moves the new name into Word. Stored values and
their formats are in [SCHEMA.md](SCHEMA.md).

## People

| Word | Means | Planned |
|---|---|---|
| owner | The one person whose life Life holds. Stored as `person:me`. In the app and user docs, "you". In prompts and what they write, his name: `{{owner}}`, filled by `readOwnerName` (his `called` in `truth/`, else his name's first word), never a pronoun. | |
| memory language | The language his memory is written in, asked at the first run beside his name: the `memoryLanguage` setting, `{{language}}` in prompts. Absent: English. Quotes stay as said; topic tags stay English. | |
| action step | One named step of an action as it passes (`recorded`, `chat_checked`, `handed`, `confirmed`; a matter marked done: `todo_items_ticked`, one per item; a new matter's Start: `goal_saved`, then the start stages; the phone's own `connection_retry`), sent as a `notifications/progress` message after the plan (`report`, `mcp-tool.ts`). Not a matter step, not a processing step, not a night step. | |
| agent | One of the owner's assistants that take his asks (a ChatGPT or Claude agent), known by its name: a key of the `agents` setting (`agentNames`), on its asks (`after.agent`) and its pairing. Nothing branches on a name. The word stored for an agent's source is `AGENT_WORD`, `agent`. | |
| pairing | How an app is approved on the connector: `bun life pair <agent>` prints a code; the app's grant (its tokens and refresh record) carries that agent's name as its agent claim, which is how the connector knows the agent (`authInfo.extra.agent`). A grant with no claim (a plain app, `bun life pair` alone) reads, but pulls no asks. `--link` prints the link the iPhone app opens (`lifelog://pair?life=<origin>&code=<code>`). | |
| speaker | Who said a turn in a recording. | |
| split group | Clean sampled turns separated from a job's speaker label by voice; recognized turn rows keep the group, which supplies no identity or evidence. | |
| Not anyone I know | The owner's answer for a voice he does not know: a stranger (status `unknown` with `basis: owner` in lifelog). The voice naming never guesses it: its guess is stored `unknown` at `weak` whatever the model said, and the score counts how many such voices a hidden run guessed a person or him (`ownAnswerOf`, `sources/lifelog-voices.ts`). Not "not relevant". | |
| not relevant | The owner's answer for a voice he won't name: maybe someone he knows, so that voice is not asked about again and is never a stranger's reference (status `not_relevant`). Not "Not anyone I know", which makes a stranger. | |
| recheck | A voice the owner named as a person that lifelog, judging without that voice's own conversations, hears as another person on at least half of its sampled turns. Only the voice eval counts them; nothing offers one to him or marks it (`rechecked` is no longer written). | |
| sample | A voice embedding of one clean recorded turn, with its model and revision; no extra audio. Unnamed samples are nobody's evidence. | |
| profile | A person's owner-attributed voice evidence, represented by one exemplar per conversation of clean clips. | |
| likeness | A voice's mean cosine to a person's closest profile exemplars; a score, not an identity or evidence. | |
| bench answer | What the owner says of a turn in the voice bench's review (one answer there names every turn of a voice's card): a person, nobody he knows, several people, not a person, or a skip. Several people and not a person leave the scoring. Kept in the bench's own file until `bench apply` sends it to lifelog's server as his correction. | |
| sender | Who wrote a message in a chat or mail. | |
| detail | A field about someone that his directory or his Contacts already holds (birthday, where they live, work, family, handles), shown on their page (`memory/details.ts`). Never stored apart from where it lives; anything else about them is a page line. | |

## The agent's work

| Word | Means | Planned |
|---|---|---|
| answer result | What `answer_check` returns (`answerWithResult`, `host/answer-result.ts`): the lines written (`done`), what `changed`, the `send`'s outcome (`sent`, `not_sent` with `canRetry`, `may_have_gone`), the `asker` and whether it was told (read once, never waited for), and `start` (a new matter's Start: the desk's start result as `change_registered_agent` gives it; null otherwise). Composed from what each store says, never stored. Not a decision's `answered` line. | |
| push id | `pushId`: a check's opaque id for a push, an HMAC of its ref under a key that stays on the Mac (`pushIdOf`, `memory/checks.ts`). The phone matches it against the inbox (the push's `pushId` field); it is never the ref. | |
| ask | The owner's words handed to the agent: from "hey &lt;agent&gt;" in a recording, or a Claude session. A ledger entry of kind `ask`; the agent pulls its own with `read_agent_asks`. | |
| onAsk | An agent's own command, in its settings, that Life starts once per new ask so the agent pulls at once. It carries no words: the agent still reads its asks with `read_agent_asks`. Not a step run. | |
| wide net | What wakes an agent on a matter besides its own wait (his word of 18 Nov 2026, `desk/matter-net.ts`): a new message from one of the matter's people, or a new message or recording of his pendant whose meaning is close to the matter's name, goal, next step or newest steps (`netOf`), by the Mac's embedder at `CLOSE_AT`. Queued as the desk event `matter.related` (its facts, and why: `person` or `meaning` with its similarity), never its words. Not a placement in the matter: the nightly matters step decides that. | |
| event | MCP's word (its Events extension, `events.ts`): what an agent waits for, polled with its own filter and cursor (`events/poll`): `message.received`, and for a paired agent its own decisions' follow-through, `decision.answered` (his answer) and `decision.lapsed` (unanswered at its deadline: it takes `onSilence`), from the cursor `request_decision` returns. Computed when polled, never stored. Not `SourceEvent`, a source's record in code, nor a calendar's event (the Past calendar's, an appointment's: the calendar's own word, in `google-calendar.ts`, `calendar-events.ts`, `appointment-events.jsonl`). | |
| mark | His words to Life, to keep: a promise that the unit is always read and every fact extracted, each at its own importance, not a statement that it matters (`marked` on the unit). Made by "hey Life" in a recording (Life's own wake, `LIFE_WAKE`; no ask), a message to himself, or `tell_life`. | |
| told-life, `tell_life` | What he tells Life in a chat: the connector's tool appends his words verbatim to `memory/told-life.jsonl`, read back as the source `told-life` ("Told Life"). Refused for an agent's token. | |
| bridge | A program that links one of his messaging accounts to his local Matrix homeserver, so Life can read LINE, Instagram, Messenger and LinkedIn (`bun life bridge`, `NETWORKS`, docs/use/bridges.md; WhatsApp's is only for sending, its reading stays the Mac app's). A network is copied from Beeper Desktop while Beeper holds it and its bridge is not linked yet (`copierOf`). Not the connector (the MCP server). | |
| app keys | The two keys of his own that a network's bridge needs in its config before it starts (Telegram's `api_id` and `api_hash` from my.telegram.org), named on its `NETWORKS` entry (`appKeys`: their config paths, which are secret, and where to get them); one still equal to the example config the bridge writes is pending (`needsAppKeys`), and `bun life bridge link` asks for it. Not a model provider's key, not a login. | |
| Beeper | Beeper Desktop, his messaging app: Life copies a network from its store (`copyBeeper`) until its bridge is linked (LINE allows one session: his word of 18 Nov 2026 moves LINE onto Life's own bridge, which replaced his 6 Nov word to keep it in Beeper). Never its API or MCP: only its store keeps what a deletion blanks long enough for the archive's copy. | |
| auto-add permission | The owner's standing permission for Life to add the to-dos he says aloud to his to-do list (`setAutoAdd`; its ledger lines are `auto_add`). | |

## The desk

| Word | Means | Planned |
|---|---|---|
| desk | The part of Life that starts and wakes his registered agents (`apps/server/src/desk/`, its own helper, store and lock; off until the `desk` setting). Holds no rule about what an agent may do. Not the watcher or a night step. | |
| registered agent | An agent the desk keeps: an id `agt_…`, a subject, a brief, a model (and effort) or its runtime's default from the desk's settings (`modelOf`), an agent wait, its sessions. Its sessions and runtime may change; its id does not. Active (a turn running or waiting), `stopped`, `handed_over` or `ended`. Not a session. "What are my agents doing?" is `readRegisteredAgents` (`host/registered-agents.ts`; the connector's `read_registered_agents`). | |
| subject | What a registered agent works on: one matter, held by its anchors, or one project of `truth/` (`agent.project`); exactly one. Never a matter id. | |
| anchor | A matter step's id by which a registered agent's matter is found (`anchor` table): the step he named first, then the rest of its matter's steps. A matter has at most one active agent holding it (`holderOf`). | |
| agent change | His word about a registered agent: start, stop, resume, re_point, change_model, hand_over (`AgentChange`). From a chat (`change_registered_agent`) it is an ask of the built-in agent `desk` (`DESK_AGENT`) with `after.agentChange`; the desk applies each once, in code (`desk/agent-changes.ts`), and writes what it did or why not (`agent_change` row). Not a `Change` of the to-do list. | |
| report line | One line a scheduled task or a session posts for the nightly report's Agents section (`bun life desk report-line`), one per source per day; shown in the next report. | |
| runtime | The program a registered agent's sessions run in (`claude`, `codex`), behind one contract (`desk/runtimes/contract.ts`), driven over the Agent Client Protocol by one `acp-runtime.ts` and a runtime row each (`runtime-rows.ts`): the CLI is found on the PATH less `node_modules/.bin` (`readProgram`), so the desk runs his CLI, never Life's pinned one. Each has `stop`, which ends the desk's own run of a session, never his app's process; a run not begun within the desk's begin limit (`BEGIN_WITHIN_MS`, 5 minutes, `agent-wait.ts`) is stopped. | |
| start stage | One of the facts the desk writes while a new agent starts, in order: `desk_accepted` (the desk took the start: the `agent_change` row with an agent id and no error; a refusal stops here), `session_open` (the `session` row), `turn_begun` (`turn.begun_at`: the model's first update after the prompt, as the ACP runtime saw it, never a process alone). `change_registered_agent` (and `answer_check`'s Start on a new matter check) reports each as it appears and ends `started`, `not_started` (the agent is ended, why in `agent.why_not_started`: its runtime refused, or its first turn ended or did not begin within the desk's begin limit) or `unconfirmed` (20 s). `goal_saved`, before them on a matter start, is the start's words saved as his `matter-direction` by `changeRegisteredAgent` itself (nothing when they already are his goal). | |
| runtime row | The data that makes the one ACP runtime a `claude` or a `codex` one (`Row`, `desk/runtimes/runtime-rows.ts`): the adapter's command and environment, the door's header, the door-tool prefix it approves, its option names for model and effort, the session's link and how a session's state is read from the program's own files. A second Life's isolation is data in its row. Not a runtime (the contract). | |
| session | One conversation of a runtime, with a link that opens it. A registered agent has one current session and its past ones. | |
| agent wait | What an active registered agent waits for: messages (`MessageFilter`), one deadline 5 minutes to 7 days ahead, and a reason. Exactly one, always. The **default wait** (24 hours, flagged) is the desk's when a turn ends with neither `set_wait` nor `finish`. Not a matter's wait step. | |
| agent wake | The desk starting an agent turn, for a cause: his answer, an event, the deadline, a retry. Not a wake word. | |
| agent turn | One run of a session the desk started, from a message to the model stopping: one ACP adapter process, ended by the prompt's reply, with its usage; a turn not begun within the desk's begin limit is stopped and ended. A turn he types in the session is his, never counted. Not a spoken turn. | |
| packet | What a fresh session starts from: the brief, the door's contract (spec 5.4), the agent's notes, its queued events, its open decision (`readPacket`). A wake starts a fresh session once the current one has grown by 30,000 tokens since its first turn (`GROWTH_LIMIT`), measured by the context the turns' usage updates report (`turn.context_used`, `session.context_at_first_call`, `growthOf`). | |
| door | The desk's loopback MCP server (`desk/desk-door.ts`, `127.0.0.1:46202/mcp/<agt_…>`), one key per registered agent (derived from the desk's key, given to its session only in its environment): `set_wait`, `finish`, `write_notes`, `request_decision`, `read_packet`; `set_wait` and `finish` only once the agent has asked a decision (its first turn's plan). The only thing the desk adds to a session. | |

## Sources

| Word | Means | Planned |
|---|---|---|
| coverage | Whether a source that captures on its own (a chat archive, mail, the pendant: `capturesOnItsOwn`) was captured on a local day: `captured` (it has a unit that day, or a publication of units read it for that day; the pendant with no unit: a recorded day; today, a readable source), `not seen` (before its first day, a day Life never read, a source a publication skipped, unreadable today, the pendant recording nothing) or `unknown` (before Life kept the record; the pendant before lifelog can tell, from the day it was last asked on, or never asked). Not silence: a quiet day is a captured day with nothing in it. | recorded days | The local days the pendant recorded on, with or without speech, as lifelog says (its `GET /recorded`): coverage's evidence for a pendant day Life holds nothing of. | physical | The source kind for what devices measure of the owner's body; an activity kind. | |
| measurement-day | One local day's Apple Health nights and workouts, each as a timed span; a night belongs to the day it began. | |
| photos | The Photos library as a source, read in place and read-only. Off until enabled in `sources`. | |
| ocr | The words Apple found in a photo (signs, screenshots of text), as a set in no text order, from its search index. Not a transcript. | |
| photo-day | A Photos unit: one local day of his library, its photos grouped by half hour and place, each line with Apple's place, scenes, who is pictured and his captions. Never an image. | |
| pictured | Who Apple's People names on a photo's faces, by name and, when Apple links a Contacts card, its handle. Not a unit's `people` (refs). | |
| scene | A label Apple's photo analysis gives a photo (beach, sunset), from its search index. Not a topic (a verdict's tag). | |
| description | Life's reading of an image, in a sentence or two: a photo's (`sources/photo-descriptions.ts`), written on the Mac by the describer, or a message file's (`description` in `files.jsonl`, written by his provider's fast model, shown as "described by Life"). One concept in two stores. Not a caption (his), not an episode's `what`. | |
| describer | The local model that writes a photo's description (`models/describer.ts`): Qwen3.5-9B under llama.cpp, started by the watcher only while photos wait. Not the embedder, not Lifelog Host's children. | |
| Voice | The voice source as the owner sees it: his recordings, through lifelog. | the app's card, Pendant today |
| conversation | What lifelog groups the owner's speech into: it ends at a confirmed Pendant pause or after 5 minutes with nobody speaking (`CONVERSATION_ENDS_AFTER`, `core/quiet.ts`). Life's voice units come from its turns. Not a spoken conversation, which Life cuts itself from the turns. | |
| spoken conversation | The owner's recorded speech cut by Life where nobody speaks for `CONVERSATION_ENDS_AFTER`, whoever was there and whatever lifelog's conversation holds them (`spokenConversationsOf`, `memory/spoken-conversations.ts`; cut by `exchangesOf`, finished by `isFinished`). Worked out from lifelog's turns each night, never stored. A voice lifelog heard from a screen, nearby or as an announcement is left out of its lines; a phone voice and one lifelog never classified are kept. Not lifelog's conversation, not a conversation-day. | |
| conversation summary | What a model wrote from every line of a spoken conversation of at least `SUMMARY_FROM_CHARS` (15,000) shown characters with a line that is not his: the summary, its subjects (each a label and the line it opens), quotes checked against their lines, and doubts about who spoke. One per part, stored as the fourth read in `memory/read-replies/` (`conversation_summary`), asked by the night (`conversationSummaries`, `memory/conversation-summaries.ts`). A voice renamed makes it pending again and hides the old one. Not a chapter (lifelog's), not an episode, not a unit's `summary`. | |
| voice naming | What a model guessed, from the part of a spoken conversation and the day around it, of who each voice nobody named is: a `voice_naming` read, one per part, stored as the fifth read in `memory/read-replies/` and shown only as a voice guess (`voiceNaming`, `memory/voice-naming.ts`; off until his `voiceNaming` setting). Not a name: a guess never acts, never reaches lifelog and never makes or folds a person. | |
| voice guess | One entry of a voice naming: the voice's `V` token, a person offered, `me` or `unknown`, the lines that show it and a confidence (`sure`, `likely`, `weak`). Kept only when it checks against what the model was shown (`checkedVoices`); `likely` with no likeness and no overlapping call is lowered to `weak`. Not his answer, not lifelog's recognition. Shown as "probably X" only in `fetch`, for sure and likely, behind his `voiceGuessesShown` setting (off until his yes, with the score's numbers): never on a speaker, in a line a step reads, in stored evidence or in the index (`memory/voice-guesses.ts`). | |
| naming brief | A few words on one possible speaker, at most 300 characters: what he is to them, their language, family and home, how often he heard them in person (the days that make them a possible speaker) and by call, last heard, and who is recorded the same days (`namingBriefOf`, `memory/naming-context.ts`). Not a person's page. | |
| possible speaker | A person who could be in a part: on a call that overlaps it, named by his answer in that conversation, heard in person in another conversation within 90 days either side (a voice his own answer named, outside a phone call with that same person, never one lifelog only matched by sound) at the UTC offset he had at the part (`isHeardAround`), in a photo of that day, or in an active fact of that day whose evidence is not a recording; at most 12, callers first (`possibleSpeakersOf`). A person who lives elsewhere and has none of these signs is not one, even when lifelog heard him by sound. | |
| the unnamed turn's key | `<turn ref> voice:<label>`, how a turn nobody named is kept in a voice naming (`unnamedTurnKey`, `memory/units.ts`), beside `turnKey` (`<turn ref> <author>`) for a named one. A voice renamed changes it, so its part is asked again. | |
| conversation part | One call's worth of a spoken conversation: at most `CONVERSATION_PART_CHARS` (150,000) characters, cut at its longest silence, lines numbered from 0 (`spokenPartsOf`). Named by the ref of its first turn; a part after the first is given the summary of the one before. Not a read part (though `person:me/conversation/<ref>` opens its summary as one). | |
| turn | One speaker's stretch of a recording, cited `<job>:<turn>@<start>`. | |
| conversation-day | A voice unit: one conversation's turns on one local day, titled by its conversation label, its words fetched only when its day is read. | |
| conversation label | The first line of a conversation-day's text and its unit's title, made by code: "Conversation at 14:05", with " with Sam, Mai" when anybody but the owner spoke (`conversationLabel`, `memory/units.ts`). Not lifelog's generated title or the owner's own title, which Life does not read. | |
| chapter | One of lifelog's summarized stretches of a conversation. A stored unit that is one (it carries lifelog's summary) is kept as stored, never built again, and its conversation gets no conversation-days. | |
| hasOwnerWrittenInThread | A mail event's flag: the owner wrote in its thread on any day (the source reads it over the whole index). Kept beside `fromMe`, which is the event's own sender. | |
| transaction | A mail Mail itself sorted as Transactions (an order, booking, receipt, delivery or bank notice), kept even from a sender he doesn't know. Not a database transaction. | |
| phone source | Phone & FaceTime call history (`phone`), copied from Apple’s store into `archive/phone.sqlite`; call-only chats keyed by remote handles or explicit participant sets; the Phone app's call log, not the owner's iPhone recordings (lifelog's `phone`). | |
| phone call | A voice or video call, on Phone & FaceTime or a messaging app: one event of its chat (including a call-only chat), with its length once it ended (0: not picked up), its line written by Life (`callLine`). "Call" alone is a model call. | |
| heard as | How lifelog heard a voice it could not name (`readVoiceKinds`): live with him, live nearby but not talking with him, over a phone, from a screen or speaker, an announcement. Its words carry it as a prefix. | |
| payment | Money he paid or got back, as his money app gives it (`apps/server/src/payments/`): not a source, never a unit nor read by a model. Placed at read time in his day, the episode it happened in (the shortest holding its time) and where he was. Not a `transaction` (a mail). | |
| paid | What was paid in an episode or a range, in EUR: money out less refunds. Not "cost" or "spend", which are model spend (`run-log.ts`). | |
| cutover | A row of an archive's `cutover` table: an instant from which the bridge's copy is read, appended once for the import of 30 Oct 2026 and once when a bridge takes over from Beeper (Beeper's newest message + 1 ms, `cutOverFromBeeper`). A bridge's version of a message in its own room, about a time before a cutover and written after it, is the earlier copy's and is not read (`asReadOf`). Never a migration: the archive only gains the row. | |
| export row | A message an export's import wrote into a chat archive (Instagram's own export, `bun life import`), its `eventId` `export:<its millisecond>`: read like any message whatever the cutover, never an arrival (`EXPORT_ROW`, `sources/archived.ts`). Not an export copy: nothing of the export is kept but these rows and the files they name. | |
| export copy | An assistant export (claude.ai or ChatGPT) Life keeps as it came in `imports/<source>/`, one per import of different bytes, never replaced or merged. Not a Life export, not the archive. | |

## The memory

| Word | Means | Planned |
|---|---|---|
| unit | The smallest piece Life reads: a conversation-day (or a stored chapter), a chat's day, a mail thread's day, a note's day, a repo's day, a device-day, a measurement-day. Id `unit_…`. | |
| arrival | New lines of a unit that no step has read yet: a burst of a chat's or a thread's messages, or a recorded conversation once lifelog closes it. Only voice, chats, mail and agents' reports arrive; notes, imports and activity are the night's. | |
| arrival gate | `arrivalsDue` (`memory/arrival-gate.ts`): model-free, it says which of today's units are due for a day pass now, or which rule holds one for the night. It decides when a unit is read, never whether: the night reads what it held. Measured by `scripts/arrival-gate-count.ts`; nothing calls it yet. | |
| verdict | A unit's judgement: its type, importance and area, with the reason. Only that. | |
| episode | A stretch of the owner's day that happened, read from the day's units and stays together; never a plan. Called moment before Nov 2026. Id `ep_…`. | |
| day part | The new units of a day that fit one call, in time order (`dayPartOf`); a day too long for one call is read in parts, each seeing the episodes the one before wrote. | |
| history month part | One piece of a history month's reading: its summary and the quotes that back it (`HistoryPart`, `personal/histories.ts`). Not a day part, not a read part. | |
| subject | What a read is about: a person, project or area (a `SubjectRef`: `person:<id>`, `project:<id>`, `area:<id>`). | |
| read part | One bounded piece of what Life holds about a subject, about `PART_CHARS` characters, opened by its ref and ending with its next reads (`memory/read-part.ts`); today a person's `now` (who and where things stand), `page`, `persona`, `story` (the years), `year` (its months' summaries), `month` (its words and days), `evidence` (observations, episodes and recorded conversations, by span, paged back) and, for him alone, `conversation` (one conversation summary, its span the ref of the turn it starts at). Not a day part, not a history month part. | |
| read part ref | A read part's id, `<subject>/<part>[/<span>][/before/<day>]` (`person:ana/evidence/2024-03`; a span is a year, YYYY, or a month, YYYY-MM), opened by `fetch` (`openById`) and `person --part`; worked out, never stored (`ReadPartRef`, `parseReadPartRef`, `readPartRefOf`). | |
| next reads | The last lines of a read part: the refs of its deeper reads, each with what it holds (`nextReads`). | |
| what | An episode's own account: what happened and what came of it, in one to three sentences. Not a unit's `summary` (lifelog's, of one conversation). | |

| talked about | The people an episode's units named without their being in it, worked out when read from its units' mentions and their placement (`talkedAboutOf`, `memory/mentions.ts`), shown by `read_day` only; never in the episode's memory line. Not "with" or "told". | |
| exchange counts | What code counts between him and one person over their one-to-one chats and mail threads, one row per exchange: who opened it, messages and deletions each way, minutes to each answer, its days (`memory/exchange-counts.ts`). Rebuilt whole from the sources each night into Life's state; folded over any span for the person read and the persona. Not a measurement (an Apple Health record), not a level (closeness), not a model's reading. | |
| exchange | One sitting of talk in a stream of messages, in time order, ended when nothing is written for 6 hours (`exchangesOf`, `EXCHANGE_ENDS_AFTER`, `memory/exchanges.ts`). The caller chooses the stream: one person's messages across channels (the exchange counts: who opened, how fast each answers) or one chat. The same cut serves speech: a spoken conversation is turns cut at 5 minutes of quiet (`CONVERSATION_ENDS_AFTER`), an exchange of messages at 6 hours. Not a passage (search's text, cut by size and 30 minutes), not lifelog's `exchanges` (turns traded in a conversation); the episodes prompt calls it a burst. A read's exchange is named by its first message's key (`eventKey`, `records/source.ts`) within the chat it was cut from. | |
| exchange batch | What one call reads when a stream's exchanges are read together: consecutive exchanges up to 30,000 characters, an exchange never cut (`batchesOf`, `EXCHANGE_BATCH_CHARS`, `memory/exchanges.ts`). Not the batches of calls a step runs side by side (`inBatches`). | |
| finished exchange | An exchange nothing was written in for the 6 hours that end one (`isFinished`, `memory/exchanges.ts`): it can no longer grow, so a read may take it. The last exchange of a chat still going is not finished. Not a closed chat (none is marked). | |
| two-way chat | A chat or a mail thread both sides wrote in (`isTwoWay`, `memory/exchanges.ts`): the ones a read of exchanges is for. One only he or only they wrote in is not. | |
| move | Something one person did toward another in an exchange, as a read lists it: its code, the line it is on, the words that show it. Who made it and when come from the message, never from the model; a move whose words are not in its exchange is dropped. Checked by `checkedMoves`, shapes in `memory/moves.ts`; every checked move is kept. Never stored: what is stored is the read reply it comes from, and moves are worked out when read. Not a trait, not a verdict on a person; not a to-do item's list move (`listMoves`), not the `changeTodoItem` command, not a mark (his words to Life). | |
| read (of exchanges) | One kind of pass a model makes over exchange batches, by its prompt: `connection`, `mentions` and `conflict` (`MOVES`, `memory/moves.ts`; the prompts, `READS`, `memory/read-replies.ts`). Each lists its own codes, so a code is counted only over the exchanges its read saw. Not `readX`, a function that reads disk or the network. | |
| read reply | What a model answered when a read took some exchanges of a one-to-one chat, or one part of a spoken conversation (the `conversation_summary` read), stored as given with what made it, the prompt digest and the keys of the messages it read (`ReadReply`, `records/read-reply.ts`; `memory/read-replies/`, a file for the month of its first message). An exchange is read by a read when a line of the read's current prompt lists it with exactly the messages it has now (`replyOf`). Not a move (worked out from a reply when read, never stored), not a fact-check answer. | |
| prompt digest | The digest of a prompt's text (16 hex), stored beside the prompt's versioned name in a read reply (`promptDigest`, `promptDigestOf`). Only the name decides whether an exchange is read again; the digest says what text made a reply. Not the prompt's version. | |
| exchange reads | The step that asks the reads of the exchanges of his two-way one-to-one chats finished in the night's days that have no stored reply: the mentions read always, the connection and conflict reads once the `relationshipReads` add-on is on (`readsOn`, `memory/exchange-reads.ts`). Reading what is stored does not wait for the add-on. Not the exchange counts (derived from the sources, no model). | |
| relationshipReads | The add-on that asks the connection and conflict reads of an exchange (`personal.relationshipReads`). The mentions read is core, with no switch. Not the exchange reads as a whole. | |
| bid | A move that invites an answer: its shape holds `answer`, toward, away or against, or none (`memory/moves.ts`). Spec 10's word; the exchange counts' "opened" is who wrote first. | |
| question case | One of the owner's questions about his life, as he asked it, with the points a right reply holds and those it must not say (`docs/evals/question-cases.json` in his data; `scripts/question-cases.ts`). Asked to a headless agent that has only the connector's reads, checked by the eval judge. Its id starts with the letter of its kind in his question set; `asker` says his own or mined from his chats. Not a regression case (an audit's, with no question), not a judge case, not a bench answer (the voice bench's). | |
| passage | What search reads as one text: a chat's consecutive messages, cut at 30 minutes of silence, 12 messages or 700 characters; a longer message or a note's version alone (`passagesOf`). Its first message's unit is its sole owner; source plus first-message id identifies it across day and month boundaries. Stored in a derived passage store, outside the search index. lifelog's search has its own, of a conversation's turns. | |
| router | A service that sends one API call to the host Life names: OpenRouter or allmodels.io (`ROUTERS`, `models/routers.ts`). Not an engine: an API engine may use several. | |
| route | One host an API engine asks, in order: a router, the model on it, the host (`routesOf`). | |
| embedder | The local model that turns a text into a vector for search by meaning (`core/embedder.ts`): EmbeddingGemma under llama.cpp, a Lifelog Host child. | |
| record | One of the zod schemas of what Life writes, in `apps/server/src/records/`, one file per record (`unit.ts`, `episode.ts`, `ledger-entry.ts`…). | |

## The phone

| Word | Means | Planned |
|---|---|---|
| read state | What one read of Life is on the phone (`ReadState`, Kit's `LifeConnector`): its last good value, when it was read, and what the latest try is doing. A screen shows `shown`: loading, loaded, empty, stale (a failed refresh after a good read), unreachable (the Mac is out of reach), failed or not paired. | |
| action state | Where one of his actions on Life stands on the phone (`ActionState`, Kit's `LifeConnector`): running with its steps, succeeded with its proof, or failed with the step, the reason and whether a retry is allowed. Only the server ends it. | |
| action step | One stage of an action as Life reports it (`ActionStep`): passed with its time, or still to come. | |
